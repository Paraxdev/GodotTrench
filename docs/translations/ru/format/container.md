# Устройство контейнера { #container-layout }

Бинарный `.tdm` это 12-байтовый заголовок файла, а затем чанки подряд до конца файла. Все числа имеют фиксированную
ширину и хранятся в порядке little endian.

| Смещение | Размер | Значение |
| --- | --- | --- |
| 0 | 8 | Сигнатура `89 47 54 4D 0D 0A 1A 0A`, то есть `\x89GTM\r\n\x1a\n` |
| 8 | 4 | Версия контейнера, u32, сейчас 1 |

Читатель отклоняет версию контейнера новее своей.

`\r\n` в сигнатуре ловит файл, прошедший преобразование концов строк, например в git. Читатель сообщает, что файл
испорчен, вместо того чтобы его читать.

## Чанки { #chunks }

Каждый чанк это 24-байтовый заголовок и затем его данные. Маркер синхронизации и проверка заголовка отличают настоящий
заголовок чанка от случайных байтов, именно так читатель находит следующий хороший чанк в [повреждённом файле](recovery.md).

| Смещение | Размер | Значение |
| --- | --- | --- |
| 0 | 4 | Маркер синхронизации `89 47 54 43`, то есть `\x89GTC` |
| 4 | 4 | Тег, четыре печатаемых символа ASCII, например `NODE` или `END ` |
| 8 | 4 | Флаги, u32. Бит 0 означает, что данные это кадр zstd |
| 12 | 4 | Исходный размер, u32, размер данных после распаковки |
| 16 | 4 | Хранимый размер, u32, число байтов данных, следующих за заголовком |
| 20 | 4 | Проверка заголовка, u32: тег, прочитанный как u32, XOR флаги, XOR исходный размер, XOR хранимый размер, XOR `0x47544D43` |

Сжатые данные это один кадр zstd с контрольной суммой содержимого. Исходный размер больше 1 GiB означает, что заголовок
повреждён, а у целого файла тоже есть [пределы](#limits).

Редактор записывает чанки в таком порядке:

1. Один чанк `HEAD`.
2. Чанки `NODE`.
3. Неизвестные чанки, которые он сохранил из загруженного файла.
4. Чанк `LMAP`, когда у карты есть запечённое освещение.
5. Чанк `END`, всегда последний.

### HEAD { #head }

[Объект верхнего уровня](README.md#top-level) без `layers`.

### NODE { #node }

Пачка целых узлов:

| Ключ | Тип | Значение |
| --- | --- | --- |
| `parents` | массив int64 | Идентификатор родителя каждого узла, 0 для слоя |
| `nodes` | массив объектов узлов | Узлы, каждый без `children` |

Узлы идут в порядке дерева, поэтому родитель всегда стоит раньше своих детей, в том же чанке или в более раннем.
Редактор начинает новый чанк, когда пачка до сжатия превышает 64 KiB, и никогда не делит узел между двумя чанками.
Благодаря этому повреждённый чанк уносит с собой только свои узлы.

Чтобы собрать дерево, добавьте каждый узел в `children` того узла, которого называет его идентификатор родителя.

### END { #end }

Чанк `END` позволяет читателю проверить, что ничего не потеряно:

| Ключ | Тип | Значение |
| --- | --- | --- |
| `version` | целое число | Версия карты, чтобы узлы загружались, даже если `HEAD` повреждён |
| `nodes` | целое число | Сколько узлов хранят чанки `NODE` |
| `chunks` | целое число | Сколько чанков идёт перед `END` |
| `content` | целое число | Идентификатор содержимого, см. ниже |

Идентификатор содержимого это 64-битный хеш FNV-1a от исходных данных `HEAD` и `NODE` в порядке файла, обрезанный до
младших 52 бит, чтобы он уцелел как число JSON. Godot хранит его вместе с построенной сценой, поэтому
[живой сеанс](../godot/live-link.md) может понять, что карта не менялась, и пропустить пересборку.

### LMAP { #lmap }

[Запечённое освещение](../editor/light-baking.md), присутствует только когда у карты есть запекание. Это один словарь с
18 ключами в собственном чанке, поэтому остальная карта загружается быстро, а старый редактор сохраняет его нетронутым.
Поскольку он большой, редактор сжимает его более быстрым уровнем zstd, чем остальные чанки. Позиции и расстояния даны в
единицах карты.

| Ключ | Тип | Значение |
| --- | --- | --- |
| `version` | целое число | Версия структуры, сейчас 1. Читатель отбрасывает запекание с более новой |
| `width`, `height` | целое число | Размер лайтмапа в текселях |
| `scene` | целое число | Отпечаток геометрии, света и неба, из которых сделано запекание, чтобы понять, что оно устарело |
| `texel_size` | float | Единиц карты на тексел |
| `light` | байты | Линейный свет, три половинных float (красный, зелёный, синий) little endian на тексел, строка за строкой |
| `shadow` | байты | Какая доля солнца достигает каждого тексела, от 0 до 255 |
| `ao` | байты | Ambient occlusion на тексел, 255 там, где рядом ничего нет |
| `chart_keys` | массив int64 | Идентификатор узла и индекс грани на каждый чарт, для ландшафта грань равна 0 |
| `chart_rows` | массив float32 | Восемь float на чарт, две строки `a b c d`, задающие координату чарта в лайтмапе от 0 до 1 как `a*x + b*y + c*z + d` |
| `nodes` | массив int64 | Пары из идентификатора узла и отпечатка его геометрии на момент запекания |
| `stale` | массив int64 | Узлы, чья геометрия с тех пор изменилась или которых больше нет. Читатели пропускают их чарты |
| `fallback` | массив float32 | Средний свет как красный, зелёный и синий, для граней без чарта |
| `probe_points` | массив float32 | Позиции световых зондов, по три float на каждую |
| `probe_sh` | массив float32 | Девять коэффициентов сферических гармоник для красного, зелёного и синего на зонд, как их хранит Godot |
| `probe_tetrahedra` | массив int32 | Четыре индекса зондов на тетраэдр |
| `probe_bsp_planes` | массив float32 | Плоскость на узел BSP, нормаль и расстояние |
| `probe_bsp_children` | массив int32 | Потомок над каждой плоскостью и под ней: другой узел, если число положительное, тетраэдр `t` как `-t - 1`, ничего как наименьшее int32 |

Ключи зондов следуют структуре `LightmapGIData` в Godot, и читатель отбрасывает зонды, когда их размеры не сходятся.
Чанк, который не удалось загрузить, отбрасывается с предупреждением, что нужно запечь заново.

В карте JSON тот же словарь лежит под ключом верхнего уровня `lightmap`, а `light`, `shadow` и `ao` записаны как текст
base64.

### Другие чанки { #other-chunks }

Читатели пропускают чанк с неизвестным тегом. Редактор сохраняет его байт в байт и при сохранении записывает обратно
после своих чанков `NODE`.

Поэтому новый чанк это способ добавить данные, которые старые редакторы переносят, не понимая их. Помните, что старый
редактор мог удалить узлы, на которые ссылается ваш чанк, так что новый тип чанка должен оставаться корректным, когда
этих узлов нет.

## Кодирование значений { #value-encoding }

Каждые данные это одно значение в бинарной сериализации Variant из Godot, формате `var_to_bytes`, с использованием
только перечисленных ниже типов. Каждое значение начинается с заголовка u32, младший байт которого это тип. Бит 16
заголовка отмечает 64-битное целое или float. Бит 16 у любого другого типа или любой другой бит делает чанк нечитаемым.
Так же делает значение внутри более чем 128 вложенных массивов и словарей.

| Тип | Заголовок | Тело |
| --- | --- | --- |
| null | 0 | Ничего |
| bool | 1 | u32, 0 или 1 |
| целое число | 2 | i32 или i64 при установленном бите 16 |
| float | 3 | f32 или f64 при установленном бите 16. Редактор всегда пишет f64 |
| строка | 4 | u32 длина в байтах, затем байты UTF-8, затем нули до кратности 4 |
| словарь | 27 | u32 число записей, затем каждый ключ (строка) и за ним его значение |
| массив | 28 | u32 число элементов, затем значения |
| байты | 29 | u32 длина, затем байты, затем нули до кратности 4 |
| массив int32 | 30 | u32 число элементов, затем по одному i32 |
| массив int64 | 31 | u32 число элементов, затем по одному i64 |
| массив float32 | 32 | u32 число элементов, затем по одному f32 |
| массив float64 | 33 | u32 число элементов, затем по одному f64 |

Читатели игнорируют бит 31 у числа записей словаря или массива, который Godot ставит для общих контейнеров, но не у
числа элементов упакованного массива. Целые числа JSON записываются как целые, а float JSON как float, поэтому
преобразование в бинарный вид и обратно даёт тот же JSON.

Чтобы файлы оставались небольшими, три вида значений получают более компактную форму. Читатель должен принимать и
компактную, и обычную:

| Значение JSON | Хранится как | Когда |
| --- | --- | --- |
| Массив из 32 или более чисел | Массив int32, когда все числа целые и помещаются. Массив float32, когда все числа float, которые 32-битный float хранит точно. Массив float64 для остальных float | Всегда |
| `heights`, `splat` и `holes` ландшафта (текст base64) | байты, декодированные данные | Когда base64 в каноническом виде |
| `instances` разброса | Один массив int32 из столбцов | Когда каждое значение это float и целое кратное своего шага |

Столбцы разброса содержат сначала индекс каждого предмета, затем каждый x и так далее через восемь полей экземпляра.
Каждое значение хранится как целое число шагов: 1 для предмета, 100 на единицу для позиции, 10 на градус для углов и
1000 для масштаба. Деление возвращает точный float, например `1234 / 100.0` это `12.34`.

> [!NOTE]
> `tdm_file.gd` превращает столбцы разброса обратно в массивы экземпляров, но байты ландшафта оставляет как
> `PackedByteArray`, а длинные массивы чисел как упакованные массивы. GDScript, который читает карту, должен принимать их
> наравне с обычными массивами.

## Пределы { #limits }

Несколько килобайт zstd могут распаковаться в гигабайты, поэтому читатель ведёт бюджет на каждый файл. Он берёт чанки
`HEAD`, `NODE`, `END` и `LMAP` в порядке файла и не читает тот, что не помещается в остаток:

1. Перед распаковкой исходный размер чанка вычитается из бюджета в 1 GiB.
2. Распакованный чанк остаётся в памяти, пока строятся его значения, поэтому его исходный размер и память его значений
   должны вместе поместиться в остаток бюджета в 1200 MiB, наряду с тем, что занимают узлы чанка `NODE`, когда из них
   строится карта. Из него вычитается только память значений и узлов. Чанк, который не помещается, ничего не забирает,
   поэтому чанки после него всё ещё можно прочитать.

Чанки с другими тегами никогда не распаковываются и ничего не забирают. Память считается так, без построения
каких-либо значений:

| Значение | Память |
| --- | --- |
| Каждое значение, включая ключи словарей и элементы упакованных массивов | 80 байт |
| Строка, сверх того | 6 байт на байт, так как JSON может записать байт как `\u0000` |
| Байты, сверх того | `4 * ceil(n / 3) + n` для `n` байт, их размер в base64 и копия, в которую их декодирует ландшафт или запекание |
| Узел чанка `NODE`, сверх его значений | 5 KiB для сущности, 12 KiB для набора разброса, 1 KiB для любого другого узла |

Стоимости узлов это верхняя оценка того, что самые маленькие узлы каждого типа занимают в редакторе после открытия
карты (группа или браш занимает около 650 байт и считается как 1 KiB), так что небольшой файл из множества крошечных
узлов не может занять больше памяти, чем бюджет. Узлы, вложенные в `children` внутри чанка `NODE`, отбрасываются, и
читатель сообщает, сколько узлов чанка их содержали, так как редактор никогда не пишет их туда. Экземпляры разброса
считаются только по своим значениям, а они составляют больше 400 байт или около того, которые редактор держит на
построенный экземпляр, поскольку все экземпляры набора делят свою модель на GPU.

Самая большая демонстрационная карта занимает 79 MiB, экземпляр разброса от 640 до 720 байт, а свет, тень и затенение
запекания при наибольшем размере атласа 299 MiB. Редактор отказывается сохранять карту, превысившую любой из пределов,
поэтому каждый записанный им файл читается целиком.
