# Протокол live link { #live-link-protocol }

Live link это то, как TrenchDot и редактор Godot разговаривают друг с другом. Аддон запускает маленький сервер внутри редактора Godot, а TrenchDot подключается к нему, чтобы запускать пересборку при сохранении, передавать правки [живого режима](live.md) и показывать, запущен ли Godot.

Эта страница вам понадобится редко, связь просто работает, как только аддон включён. Она нужна на случай, когда вы пишете собственный инструмент, который управляет Godot так же, или хотите выяснить, почему соединение не устанавливается. Если сохранение не запускает пересборку, начните лучше с раздела [Пересборка при сохранении](live.md#rebuild-on-save), строка состояния обычно объясняет причину.

## Транспорт { #transport }

Построчный JSON (newline delimited JSON) по TCP на `127.0.0.1:7842`. Каждое сообщение содержит `event` и необязательный `seq`, и на него приходит ровно одна строка ответа, которая повторяет `seq` и содержит `ok`. При ошибке ответ содержит `ok: false` и `error`. Редактор держит одно соединение открытым и раз в секунду шлёт heartbeat `status`.

Чтобы использовать другой порт, измените его с обеих сторон: `trenchdot/live_link_port` в настройках проекта Godot и *Live Link с Godot* в *Файл > Настройки* в TrenchDot.

[Горячая перезагрузка](live.md#hot-reload-in-a-running-game), то есть автозагрузка в запущенной игре, слушает `127.0.0.1:7843` и отвечает только на `map_saved`.

## События { #events }

Клиент отправляет эти события. В столбце «Ответ» перечислены поля, которыми Godot отвечает помимо `ok` и `seq`, или то, что он делает.

| Событие | Поля | Ответ |
| --- | --- | --- |
| `hello` | | `project` и `godot` (версия), быстрая проверка, что связь отвечает |
| `status` | | `project`, `godot` (версия), `pid`, `scene` (вкладка сцены, которую показывает Godot) и `maps: [{path, epoch}]` для неё |
| `map_saved` | `path` | `rebuilt`, число узлов карты, пересобранных из файла, `scene`, `waiting`, а также `missing_classes`, `settings` и `warnings` этой сборки |
| `build` | `path`, `text` | Как `map_saved`, но сборка идёт из `text`, а не из файла |
| `focus` | | Выводит окно Godot на передний план |
| `export_game_config` | | Записывает `trenchdot_game.json` |
| `scan` | | Запускает сканирование файлов проекта. Когда оно закончится, каждая живая сессия проверит свои определения сущностей |
| `play` | | Сохраняет открытые сцены и запускает главную сцену, а если в проекте её нет, отвечает `ok: false` и `error` |
| `live_begin` | `path`, `text`, `content` | `epoch` и `unresolved` |
| `live_resync` | `path`, `text` | `epoch` и `unresolved` |
| `live_delta` | `path`, `ops` | `epoch` и `unresolved`, или `ok: false, resync: true`, если операции не подходят |
| `live_end` | `path`, `revert` | С `revert` пересобирает из сохранённого файла |
| `inspect` | `path`, `ids` | `nodes` с именем, классом, числом потомков и позицией для каждого id узла карты, а также `live` и `pending` |
| `capture` | `path`, `camera`, `width`, `height`, `text` | `png` (base64), `width`, `height` и `warnings`, то есть ошибки и предупреждения, записанные во время сборки |
| `walkable` | `path`, `agent`, `text` | `vertices` (плоский список x, y, z), `polygons`, `islands` (индексы полигонов, самый большой первым), `units_per_meter`, `agent` и `msec` |

`capture` рендерит мир первого узла карты, использующего `path`. В `camera` лежат `position` и `forward` в единицах и осях карты и `fov`, горизонтальный угол обзора в градусах. С `text` Godot сначала собирает эту карту, иначе он ждёт, пока живая сессия догонит. Ответ приходит примерно через дюжину кадров, а другие сообщения тем временем обрабатываются.

`walkable` запекает навигационный меш всей редактируемой сцены через `TrenchDotNav` для `agent` (`radius`, `height`, `max_climb`, `max_slope` в метрах и градусах) и возвращает его в единицах и осях карты. С `text` Godot сначала собирает эту карту, если только она уже не была в последний раз собрана из того же текста.

Пути абсолютные, со слэшами вперёд. Участвуют только узлы `FuncGodotMap` в редактируемой сцене, то есть на вкладке сцены, которую показывает Godot, с включённым *Auto Rebuild On Save*. `scene` это её путь `res://`, а если сцена не открыта, значение пустое.

`waiting` перечисляет остальные открытые вкладки сцен, которые используют карту. После `map_saved` они собирают файл, когда их вкладку показывают, после `build` не собирают. `map_saved` для префаба также пересобирает карты редактируемой сцены, которые его создают, напрямую или через другие префабы, и учитывает их в `rebuilt`.

То, о чём сообщили сборки после `map_saved` или `build`, приходит в трёх списках, каждый только когда он не пуст: `missing_classes` содержит отсортированные имена классов, которые не описало ни одно определение, `settings` пути к настройкам карты, которые использовали сборки, а `warnings` до 20 однострочных предупреждений из отчёта сборки. `unresolved` в живом ответе перечисляет отсортированные имена классов, которые этот шаг собрал без определения, тоже только если такие есть.

`scan` подходит для файлов, записанных вне Godot, например установленного пакета сущностей. Живая сессия, сцена которой была собрана с другими определениями сущностей, чем лежат в её настройках карты после сканирования, собирает карту заново. Аддон без `scan` или `play` отвечает на них как на неизвестное событие.

`text` это вся карта в виде JSON, а запечённое освещение лежит в `lightmap`, если у карты есть запекание, так что живая сборка его сохраняет. Это добавляет около 11 байт на тексел атласа, около 11 МБ для атласа 1024 на 1024, поэтому редактор отправляет всю карту снова только при старте сессии, после нового запекания или после большого изменения.

`content` это id содержимого в чанке END сохранённого файла, поэтому сцена, собранная из неизменённого файла, не собирается снова при старте сессии.

Если порт занят, обычно вторым редактором Godot с тем же проектом, аддон один раз предупреждает в панели Output и пробует порт снова каждые три секунды, так что он займёт его, когда другой редактор закроется.

## Живые операции { #live-ops }

| Операция | Поля | Значение |
| --- | --- | --- |
| `set` | `id`, `parent`, `index`, `node` | Вставить или заменить узел, в JSON-форме формата `.tdm`, без потомков |
| `remove` | `id` | Удалить узел вместе с поддеревом, отправляется только самый верхний удалённый id |
| `translate` | `ids`, `offset` | Сдвинуть узлы, отправляется при перетаскивании вместо геометрии |
| `properties` | `properties` | Заменить свойства worldspawn |

`epoch` карты растёт всякий раз, когда её собирают вне живой сессии или когда меняются узлы `FuncGodotMap`, которые её используют. Когда следующий `status` покажет новую эпоху, начните заново с `live_begin`.

Сгенерированные узлы несут id своего узла карты в метаданных `_td_id`, а узлы слоёв и групп в `_td_group`.

## Проверка без окна { #testing-without-a-window }

Связь работает и с headless-редактором Godot, что удобно для автоматических тестов. Откройте сцену с `FuncGodotMap`, затем отправьте `inspect` на порт 7842, чтобы увидеть, что собрал Godot:

```sh
godot --headless --editor --path godot res://path/scene.tscn
```

(Примечание: на свежем чекауте сначала дважды выполните `godot --headless --path godot --import`. Одного прохода хватает только на то, чтобы зарегистрировать классы аддона.)

Headless Godot ничего не рисует, поэтому `capture` отвечает там ошибкой. Проверяйте снимки в редакторе с окном.

Тесты аддона делают именно это в
[`godot/tests/editor/live_link_tabs.gd`](https://github.com/Paraxdev/TrenchDot/blob/main/godot/tests/editor/live_link_tabs.gd),
который открывает, закрывает, перезагружает и переключает вкладки сцен в headless-редакторе и проверяет, о чём сообщает связь.

## MCP { #mcp }

[MCP-сервер](../mcp.md) позволяет агентам и скриптам управлять редактором, а некоторые его инструменты идут через live link. Инструмент `screenshot` использует `capture`, когда просят картинку из Godot.

Для headless-тестов, которые тоже правят карту, запустите TrenchDot с его MCP-сервером на том же проекте, что и headless-редактор Godot, и правьте карту через MCP:

```sh
trenchdot --mcp-http --project godot
```
