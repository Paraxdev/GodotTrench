# コンテナの構造 { #container-layout }

バイナリの`.tdm`は、12バイトのファイルヘッダーに続いて、ファイルの終わりまでチャンクが隙間なく並んだものです。数値はすべてリトルエンディアンの固定幅です。

| オフセット | サイズ | 意味 |
| --- | --- | --- |
| 0 | 8 | マジック`89 47 54 4D 0D 0A 1A 0A`、つまり`\x89GTM\r\n\x1a\n` |
| 8 | 4 | コンテナのバージョン、u32、現在は1 |

リーダーは、自分より新しいコンテナバージョンを拒否します。

マジックの`\r\n`は、たとえばgitなどで改行コードの変換を通ってしまったファイルを検出するためのものです。リーダーはそのファイルを読まず、壊れていると報告します。

## チャンク { #chunks }

各チャンクは、24バイトのヘッダーとそれに続くペイロードでできています。同期マーカーとヘッダーチェックのおかげで、本物のチャンクヘッダーとランダムなバイト列を見分けられます。[壊れたファイル](recovery.md)で、リーダーが次の正常なチャンクを見つけられるのはこのためです。

| オフセット | サイズ | 意味 |
| --- | --- | --- |
| 0 | 4 | 同期マーカー`89 47 54 43`、つまり`\x89GTC` |
| 4 | 4 | タグ。`NODE`や`END `のような、表示可能なASCII文字4つ |
| 8 | 4 | フラグ、u32。ビット0が立っていると、ペイロードはzstdフレームです |
| 12 | 4 | 展開後のサイズ、u32、解凍後のペイロードのサイズ |
| 16 | 4 | 保存サイズ、u32、ヘッダーの後に続くペイロードのバイト数 |
| 20 | 4 | ヘッダーチェック、u32。タグをu32として読んだ値、XOR フラグ、XOR 展開後のサイズ、XOR 保存サイズ、XOR `0x47544D43` |

圧縮されたペイロードは、コンテンツチェックサム付きのzstdフレーム1つです。展開後のサイズが1 GiBを超えていたら、ヘッダーが壊れています。ファイル全体にも[上限](#limits)があります。

エディターは次の順でチャンクを書きます。

1. `HEAD`チャンクを1つ。
2. `NODE`チャンク。
3. 読み込んだファイルから引き継いだ、未知のチャンク。
4. マップにベイクしたライティングがあるなら、`LMAP`チャンク。
5. `END`チャンク。常に最後です。

### HEAD { #head }

`layers`を除いた[トップレベルのオブジェクト](README.md#top-level)です。

### NODE { #node }

丸ごとのノードをまとめたバッチです。

| キー | 型 | 意味 |
| --- | --- | --- |
| `parents` | int64の配列 | 各ノードの親id。レイヤーは0です |
| `nodes` | ノードオブジェクトの配列 | ノード本体。それぞれ`children`は持ちません |

ノードはツリーの順に並んでいるので、親は必ず子より前に来ます。同じチャンクの中か、前のチャンクにあります。エディターは、バッチが圧縮前に64 KiBを超えたら新しいチャンクを始め、1つのノードを2つのチャンクにまたがらせることはしません。こうしておけば、壊れたチャンクが巻き込むのはそのチャンクのノードだけで済みます。

ツリーを組み立てるには、各ノードを、その親idが指すノードの`children`に追加していきます。

### END { #end }

`END`チャンクを使うと、リーダーは欠けているものがないかを確認できます。

| キー | 型 | 意味 |
| --- | --- | --- |
| `version` | integer | マップのバージョン。`HEAD`が壊れていても、ノードは読み込めます |
| `nodes` | integer | `NODE`チャンクが持つノードの数 |
| `chunks` | integer | `END`より前にあるチャンクの数 |
| `content` | integer | コンテンツid。下を参照してください |

コンテンツidは、生の`HEAD`と`NODE`のペイロードをファイルの順に並べた64ビットのFNV-1aハッシュを、JSONの数値として扱えるように下位52ビットに切り詰めたものです。Godotは組み立てたシーンと一緒にこれを保持するので、[ライブセッション](../godot/live-link.md)はマップが変わっていないことを判断して、再構築を省けます。

### LMAP { #lmap }

[ベイクしたライティング](../editor/light-baking.md)で、マップにベイクがあるときだけ存在します。18個のキーを持つ1つの辞書で、専用のチャンクに入っているので、残りのマップは速く読み込めますし、古いエディターもそのまま保持します。大きいので、エディターはほかのチャンクより速いzstdレベルで圧縮します。位置と距離はマップ単位です。

| キー | 型 | 意味 |
| --- | --- | --- |
| `version` | integer | レイアウトのバージョン、現在は1。リーダーは、それより新しいベイクを捨てます |
| `width`, `height` | integer | ライトマップのサイズ(テクセル) |
| `scene` | integer | ベイクの元になったジオメトリ、ライト、空のフィンガープリント。古くなったかどうかの判定に使います |
| `texel_size` | float | テクセルあたりのマップ単位 |
| `light` | bytes | リニアな光。テクセルごとにリトルエンディアンのハーフフロート3つ(赤、緑、青)を、行ごとに並べます |
| `shadow` | bytes | 各テクセルに届く太陽光の量、0から255 |
| `ao` | bytes | テクセルごとのアンビエントオクルージョン。近くに何もなければ255 |
| `chart_keys` | int64の配列 | チャートごとのノードidと面インデックス。地形では面は0です |
| `chart_rows` | float32の配列 | チャートごとに8つのfloat。`a b c d`の2行で、チャートの0から1のライトマップ座標を`a*x + b*y + c*z + d`で与えます |
| `nodes` | int64の配列 | ノードidと、ベイク時のそのジオメトリのフィンガープリントのペア |
| `stale` | int64の配列 | その後ジオメトリが変わった、またはなくなったノード。リーダーはそのチャートをスキップします |
| `fallback` | float32の配列 | チャートのない面のための、平均の光(赤、緑、青) |
| `probe_points` | float32の配列 | ライトプローブの位置。1つにつきfloat 3つ |
| `probe_sh` | float32の配列 | プローブごとに、赤、緑、青それぞれ9個の球面調和関数の係数。Godotの保存形式のままです |
| `probe_tetrahedra` | int32の配列 | 四面体ごとに4つのプローブインデックス |
| `probe_bsp_planes` | float32の配列 | BSPノードごとの平面。法線と距離です |
| `probe_bsp_children` | int32の配列 | 各平面の手前側と奥側の子。正の値なら別のノード、四面体`t`なら`-t - 1`、何もなければint32の最小値 |

プローブのキーはGodotの`LightmapGIData`のレイアウトに従っていて、サイズが合わないときリーダーはプローブを除外します。読み込みに失敗したチャンクは、もう一度ベイクするよう警告を出して捨てられます。

JSONのマップでは、同じ辞書がトップレベルの`lightmap`キーの下にあり、`light`、`shadow`、`ao`はbase64のテキストになります。

### ほかのチャンク { #other-chunks }

リーダーは、知らないタグのチャンクをスキップします。エディターはそれをバイト単位でそのまま保持し、保存時に`NODE`チャンクの後に書き戻します。

つまり、古いエディターが中身を理解しないまま持ち運んでくれるデータを追加したいなら、新しいチャンクを作ります。ただし、古いエディターは、あなたのチャンクが参照するノードを削除しているかもしれません。新しいチャンクの種類は、それらのノードがなくなっても有効なままでなければなりません。

## 値のエンコード { #value-encoding }

各ペイロードは、Godotのバイナリ形式のVariantシリアライズ(`var_to_bytes`の形式)の値1つで、使うのは下の型だけです。どの値も、下位バイトが型を表すu32のヘッダーで始まります。ヘッダーのビット16は、64ビットの整数か浮動小数点数を示します。ほかの型でビット16が立っていたり、ほかのビットが立っていたりすると、そのチャンクは読めなくなります。配列や辞書が128個より深く入れ子になっている値も同じです。

| 型 | ヘッダー | 本体 |
| --- | --- | --- |
| null | 0 | なし |
| bool | 1 | u32、0か1 |
| integer | 2 | i32、ビット16が立っていればi64 |
| float | 3 | f32、ビット16が立っていればf64。エディターは常にf64で書きます |
| string | 4 | u32のバイト長、UTF-8のバイト列、4の倍数になるまでのゼロパディング |
| dictionary | 27 | u32の個数、続いてキー(文字列)とその値の組 |
| array | 28 | u32の個数、続いて値 |
| bytes | 29 | u32の長さ、バイト列、4の倍数になるまでのゼロパディング |
| int32 array | 30 | u32の個数、続いてi32を1つずつ |
| int64 array | 31 | u32の個数、続いてi64を1つずつ |
| float32 array | 32 | u32の個数、続いてf32を1つずつ |
| float64 array | 33 | u32の個数、続いてf64を1つずつ |

リーダーは、辞書や配列の個数のビット31(Godotが共有コンテナに立てるもの)は無視しますが、パック配列の個数では無視しません。JSONの整数は整数として、JSONの浮動小数点数は浮動小数点数として書かれるので、バイナリに変換して戻しても同じJSONになります。

ファイルを小さく保つために、3種類の値はよりコンパクトな形で保存されます。リーダーは、コンパクトな形と通常の形のどちらも受け付けなければなりません。

| JSONの値 | 保存される形 | いつ |
| --- | --- | --- |
| 32個以上の数値の配列 | すべてが収まる整数ならint32の配列。すべてが32ビットfloatで正確に表せる浮動小数点数ならfloat32の配列。それ以外の浮動小数点数ならfloat64の配列 | 常に |
| 地形の`heights`、`splat`、`holes`(base64のテキスト) | bytes、デコードしたデータ | base64が正規の形のとき |
| 散布の`instances` | 列をまとめたint32の配列1つ | すべての値がfloatで、それぞれのステップの整数倍のとき |

散布の列には、まずすべてのアイテムインデックス、次にすべてのx、というように、インスタンスの8つのフィールドを順に並べます。各値は、そのステップの整数個として保存されます。アイテムは1、位置は1単位あたり100、角度は1度あたり10、スケールは1000です。割り算で正確なfloatに戻り、たとえば`1234 / 100.0`は`12.34`です。

> [!NOTE]
> `tdm_file.gd`は、散布の列をインスタンスの配列に戻しますが、地形のバイト列は`PackedByteArray`のまま、長い数値の配列もパック配列のままにします。マップを読むGDScriptは、普通の配列に加えてこれらも受け付ける必要があります。

## 上限 { #limits }

数キロバイトのzstdが数ギガバイトに展開されることもあるので、リーダーはファイルごとに予算を持ちます。`HEAD`、`NODE`、`END`、`LMAP`のチャンクをファイルの順に取り、残りに収まらないものは読みません。

1. 展開する前に、チャンクの展開後のサイズを1 GiBの予算から差し引きます。
2. 展開したチャンクは、その値を作っている間メモリに残ります。そのため、展開後のサイズと値のメモリを合わせて、1200 MiBの予算の残りに収まる必要があります。`NODE`チャンクのノードをマップに組み立てたときに使うメモリも、この予算に含まれます。予算から引かれるのは、値とノードのメモリだけです。収まらないチャンクは何も消費しないので、その後ろのチャンクはまだ読めます。

ほかのタグのチャンクは展開されず、何も消費しません。メモリは、値を実際に作らずに次のように数えます。

| 値 | メモリ |
| --- | --- |
| すべての値(辞書のキーとパック配列の要素も含む) | 80バイト |
| 文字列には、さらに | 1バイトにつき6バイト。JSONは1バイトを`\u0000`と書くことがあるためです |
| bytesには、さらに | `n`バイトに対して`4 * ceil(n / 3) + n`。base64にしたときのサイズと、地形やベイクがそれをデコードして作るコピーの分です |
| `NODE`チャンクのノードには、値に加えて | エンティティは5 KiB、散布セットは12 KiB、そのほかのノードは1 KiB |

ノードのコストは、エディターがマップを開いたときに各種類の最小のノードが使うメモリの上限です(グループやブラシは約650バイトですが、1 KiBとして計上します)。そのため、小さなノードがたくさん入った小さなファイルが、予算を超えるメモリを使うことはありません。`NODE`チャンクの`children`の下に入れ子になったノードは捨てられ、リーダーは、チャンクのノードのうちいくつがそれを持っていたかを報告します。エディターはそこには書かないからです。散布のインスタンスは値だけで数えます。これは、エディターが作成済みのインスタンス1つに持つ400バイト前後より大きくなりますが、それはセットのすべてのインスタンスが、GPU上で同じモデルを共有しているためです。

最大のショーケースマップは79 MiB、散布のインスタンスは1つ640から720バイト、最大のアトラスサイズでのベイクのライト、シャドウ、オクルージョンは299 MiBです。エディターはどちらかの上限を超えるマップの保存を拒否するので、エディターが書いたファイルはすべて最後まで読めます。
