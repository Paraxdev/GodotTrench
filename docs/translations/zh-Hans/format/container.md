# 容器结构 { #container-layout }

二进制 `.tdm` 先是 12 字节的文件头，然后是一个接一个紧挨着的数据块，直到文件结束。每个数字都是小端序、定长的。

| 偏移 | 大小 | 含义 |
| --- | --- | --- |
| 0 | 8 | 魔数 `89 47 54 4D 0D 0A 1A 0A`，也就是 `\x89GTM\r\n\x1a\n` |
| 8 | 4 | 容器版本，u32，目前是 1 |

读取器会拒绝比自己版本更新的容器版本。

魔数里的 `\r\n` 用来发现经过换行符转换的文件，比如在 git 里被转换过的。读取器会把这样的文件报告为已损坏，而不是去读它。

## 数据块 { #chunks }

每个数据块是 24 字节的头，后面跟着它的负载。同步标记和头校验让读取器分辨出真正的数据块头和随机字节，读取器就是这样在[损坏的文件](recovery.md)里找到下一个完好数据块的。

| 偏移 | 大小 | 含义 |
| --- | --- | --- |
| 0 | 4 | 同步标记 `89 47 54 43`，也就是 `\x89GTC` |
| 4 | 4 | 标签，四个可打印的 ASCII 字符，比如 `NODE` 或 `END ` |
| 8 | 4 | 标志，u32。第 0 位表示负载是一个 zstd 帧 |
| 12 | 4 | 原始大小，u32，负载解压后的大小 |
| 16 | 4 | 存储大小，u32，头后面跟着的负载字节数 |
| 20 | 4 | 头校验，u32：把标签当作 u32 读出，异或标志，异或原始大小，异或存储大小，异或 `0x47544D43` |

压缩的负载是一个带内容校验和的 zstd 帧。原始大小超过 1 GiB 说明头已损坏，整个文件还有[上限](#limits)。

编辑器按这个顺序写数据块：

1. 一个 `HEAD` 数据块。
2. 若干 `NODE` 数据块。
3. 它从所加载的文件里保留下来的所有未知数据块。
4. 地图有烘焙光照时，一个 `LMAP` 数据块。
5. `END` 数据块，永远在最后。

### HEAD { #head }

没有 `layers` 的[顶层对象](README.md#top-level)。

### NODE { #node }

一批完整的节点：

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `parents` | int64 数组 | 每个节点的父节点 id，图层为 0 |
| `nodes` | 节点对象数组 | 这些节点，每个都不带 `children` |

节点按树的顺序排列，所以父节点总是在它的子节点之前，在同一个数据块里或更早的数据块里。一批节点压缩前超过 64 KiB 时，编辑器就开一个新的数据块，而且绝不会把一个节点拆到两个数据块里。这样一个损坏的数据块只会带走它自己的节点。

要重建这棵树，把每个节点追加到它的父节点 id 所指节点的 `children` 里。

### END { #end }

`END` 数据块让读取器能检查有没有缺东西：

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `version` | 整数 | 地图版本，这样 `HEAD` 损坏时节点仍然能加载 |
| `nodes` | 整数 | `NODE` 数据块里一共有多少节点 |
| `chunks` | 整数 | `END` 之前有多少数据块 |
| `content` | 整数 | 内容 id，见下 |

内容 id 是按文件顺序对原始 `HEAD` 和 `NODE` 负载做的 64 位 FNV-1a 哈希，截取低 52 位，这样它能以 JSON 数字的形式保存下来。Godot 会把它和构建出的场景存在一起，这样[实时会话](../godot/live-link.md)就能判断地图没有变化并跳过重建。

### LMAP { #lmap }

[烘焙光照](../editor/light-baking.md)，只在地图有烘焙时才有。它是一个有 18 个键的字典，放在单独的数据块里，这样地图其余部分加载得快，旧版编辑器也会原封不动地保留它。因为它很大，编辑器用比其他数据块更快的 zstd 级别压缩它。位置和距离的单位是地图单位。

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `version` | 整数 | 布局版本，目前是 1。读取器会丢弃版本更新的烘焙 |
| `width`、`height` | 整数 | 光照贴图的大小，单位是纹素 |
| `scene` | 整数 | 烘焙所依据的几何、灯光和天空的指纹，用来判断它是否过期 |
| `texel_size` | 浮点数 | 每纹素的地图单位数 |
| `light` | 字节 | 线性光，每个纹素三个小端序半精度浮点数（红、绿、蓝），逐行排列 |
| `shadow` | 字节 | 每个纹素能照到多少太阳光，0 到 255 |
| `ao` | 字节 | 每个纹素的环境光遮蔽，附近没有东西时为 255 |
| `chart_keys` | int64 数组 | 每个图表一个节点 id 和一个面索引，地形的面索引为 0 |
| `chart_rows` | float32 数组 | 每个图表八个浮点数，两行 `a b c d`，按 `a*x + b*y + c*z + d` 给出图表的 0 到 1 光照贴图坐标 |
| `nodes` | int64 数组 | 成对的节点 id 和它烘焙时的几何指纹 |
| `stale` | int64 数组 | 几何在那之后改动过或已经消失的节点。读取器会跳过它们的图表 |
| `fallback` | float32 数组 | 平均光，红、绿、蓝各一个，给没有图表的面用 |
| `probe_points` | float32 数组 | 光照探针的位置，每个三个浮点数 |
| `probe_sh` | float32 数组 | 每个探针九组红、绿、蓝球谐系数，和 Godot 存储的一样 |
| `probe_tetrahedra` | int32 数组 | 每个四面体四个探针索引 |
| `probe_bsp_planes` | float32 数组 | 每个 BSP 节点一个平面，法线和距离 |
| `probe_bsp_children` | int32 数组 | 每个平面上方和下方的子项：为正时是另一个节点，四面体 `t` 记作 `-t - 1`，没有则是最小的 int32 |

探针的键遵循 Godot 的 `LightmapGIData` 的布局，探针的大小对不上时，读取器会把探针去掉。加载失败的数据块会被丢弃，并给出重新烘焙的警告。

在 JSON 地图里，同样的字典位于顶层的 `lightmap` 键下，`light`、`shadow` 和 `ao` 是 base64 文本。

### 其他数据块 { #other-chunks }

读取器会跳过标签不认识的数据块。编辑器把它逐字节保留，保存时写回到它的 `NODE` 数据块之后。

所以，想加一份旧版编辑器会带着走、却不必看懂的数据，新增一种数据块就是办法。要记住，旧版编辑器可能已经删掉了你的数据块所指的节点，所以新的数据块类型在这些节点消失后也必须保持有效。

## 值的编码 { #value-encoding }

每个负载是一个值，用 Godot 的二进制 Variant 序列化，也就是 `var_to_bytes` 的格式，只使用下面这些类型。每个值都以一个 u32 头开始，它的低字节是类型。头的第 16 位标记 64 位整数或浮点数。其他类型上带第 16 位，或者带任何其他位，都会让这个数据块无法读取。嵌套超过 128 层数组和字典的值也一样。

| 类型 | 头 | 主体 |
| --- | --- | --- |
| null | 0 | 无 |
| 布尔 | 1 | u32，0 或 1 |
| 整数 | 2 | i32，设置了第 16 位时是 i64 |
| 浮点数 | 3 | f32，设置了第 16 位时是 f64。编辑器总是写 f64 |
| 字符串 | 4 | u32 字节长度，然后是 UTF-8 字节，再用零补齐到 4 的倍数 |
| 字典 | 27 | u32 个数，然后是每个键（一个字符串）和它的值 |
| 数组 | 28 | u32 个数，然后是各个值 |
| 字节 | 29 | u32 长度，然后是这些字节，再用零补齐到 4 的倍数 |
| int32 数组 | 30 | u32 个数，然后每项一个 i32 |
| int64 数组 | 31 | u32 个数，然后每项一个 i64 |
| float32 数组 | 32 | u32 个数，然后每项一个 f32 |
| float64 数组 | 33 | u32 个数，然后每项一个 f64 |

读取器会忽略字典或数组个数的第 31 位（Godot 为共享容器设置它），但不会忽略紧凑数组个数的第 31 位。JSON 的整数写成整数，JSON 的浮点数写成浮点数，所以转成二进制再转回来，得到的 JSON 不变。

为了让文件保持小巧，三类值有更紧凑的形式。读取器必须同时接受紧凑形式和普通形式：

| JSON 值 | 存成 | 何时 |
| --- | --- | --- |
| 32 个或更多数字的数组 | 全是装得下的整数时存成 int32 数组。全是 32 位浮点数能精确容纳的浮点数时存成 float32 数组。其他浮点数存成 float64 数组 | 总是 |
| 地形的 `heights`、`splat` 和 `holes`（base64 文本） | 字节，也就是解码后的数据 | base64 是规范形式时 |
| 散布的 `instances` | 一个由各列组成的 int32 数组 | 每个值都是浮点数，并且是它步长的整数倍时 |

散布的列先放所有的条目索引，再放所有的 x，依此类推，一直到一个实例的八个字段。每个值都存成它步长的整数个数：条目是 1，位置是每单位 100，角度是每度 10，缩放是 1000。除回去就得到精确的浮点数，例如 `1234 / 100.0` 是 `12.34`。

> [!NOTE]
> `tdm_file.gd` 会把散布的列还原成实例数组，但地形的字节仍是 `PackedByteArray`，长的数字数组仍是紧凑数组。读取地图的 GDScript 除了普通数组，也要能接受这些。

## 上限 { #limits }

几 KB 的 zstd 可以解压成几 GB，所以读取器会给每个文件设预算。它按文件顺序处理 `HEAD`、`NODE`、`END` 和 `LMAP` 数据块，装不进剩余预算的数据块就不读：

1. 解压之前，数据块的原始大小要从 1 GiB 的预算里扣掉。
2. 解压出来的数据块在构建它的值期间一直留在内存里，所以它的原始大小和它的值占用的内存，要一起装进 1200 MiB 的预算所剩的部分，此外还有 `NODE` 数据块里的节点在地图据此构建后占用的内存。只有值和节点的内存会从预算里扣掉。装不下的数据块什么都不占，所以它后面的数据块仍然可以读取。

带其他标签的数据块从不解压，也不占预算。内存按下面的方式计算，不需要真的构建任何值：

| 值 | 内存 |
| --- | --- |
| 每个值，包括字典的键和紧凑数组的各项 | 80 字节 |
| 字符串，另加 | 每字节 6 字节，因为 JSON 可能把一个字节写成 `\u0000` |
| 字节，另加 | `n` 字节为 `4 * ceil(n / 3) + n`，也就是它们作为 base64 的大小，加上地形或烘焙把它们解码进去的那份副本 |
| `NODE` 数据块的一个节点，在它的值之外另加 | 实体 5 KiB，散布集合 12 KiB，其他节点 1 KiB |

节点的开销是各类型最小的节点在编辑器打开地图后所占内存的上界（一个组或笔刷约为 650 字节，按 1 KiB 计），所以一个由许多极小节点组成的小文件占用的内存不会超出预算。`NODE` 数据块里嵌在 `children` 下的节点会被丢弃，读取器会报告该数据块里有多少节点带了子节点，因为编辑器从不会把它们写在那里。散布实例只按它们的值计数，这比编辑器为一个构建好的实例保留的 400 字节左右要多，因为一个集合的所有实例在 GPU 上共用它的模型。

最大的展示地图占 79 MiB，一个散布实例占 640 到 720 字节，最大图集尺寸下一次烘焙的光、阴影和遮蔽占 299 MiB。编辑器拒绝保存超过任一上限的地图，所以它写出的每个文件都能完整读取。
